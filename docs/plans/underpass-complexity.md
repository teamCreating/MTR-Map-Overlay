# 真实高度上下穿遮挡：时空复杂度

日期：2026-10-21（Asia/Taipei），Codex。基线 `b08d5af`，版本保持 **1.5.2**。依据当前 HeightMapScene、RouteRibbonGeometry、MapTrack 和两个地图渲染器；本轮不修改运行功能。

结论：需求本身不要求逐车厢与全部轨道两两相交。现有实现使用细分画家算法，主要为可见几何生成 O(Q)、比较排序 O(Q log Q)、绘制和悬停 O(Q)。更完整的成本还包括每帧全轨道/输入车厢扫描、候选轨道的线段检查、片段分配和 GPU 像素覆盖。优先消除静态重复工作与临时对象；严格的局部遮挡可再评估独立深度渲染通道。

## 1. 分析边界与符号

需求是“已知真实 XYZ 的轨道、路线和车厢，在同一地图投影中按局部高度遮挡，并使 hover 与可见结果一致”。不包含地形、建筑、桥面实体或隧道顶板采集；增加这些遮挡物是另一项数据/几何任务，不能用当前复杂度代表。

位置采集、Core 路径求解与网络同步在渲染之前；下列主公式从已有 MapTrack/MapCar 输入开始，不把它们的成本藏入绘制时间。

| 符号 | 定义 |
| --- | --- |
| R | 当前维度输入的物理轨道对象数，含屏外轨道 |
| A | 这些轨道的线路色带条目总数；关闭路线层时可以省去相应工作 |
| P | 包围盒与视口相交的候选轨道所含全部采样线段数，不等于真正可见线段数 |
| J | 通过逐线段视口裁剪的线段数 |
| H | 上述线段尝试遍历的高度分片数之和，包含最终与裁剪区间不相交的片段 |
| K_i | 某物理轨道上的共线线路数量；当前只限制总宽，没有硬性限制条目数量 |
| B | 实际生成的高铁白块四边形数量，含被高度切分再次分开的白块 |
| C | 输入 MapCar 总数，含屏外车厢 |
| Q_s / Q_d | 最终可见静态/动态四边形数量；Q = Q_s + Q_d |
| P_x | 渲染目标像素数 W×H，区别于采样线段数 P |
| F | GPU 处理的片元候选总数，包含重叠/被遮挡部分 |

MapTrack 缓存包围盒、法线及累计距离，因此单次包围盒检查是 O(1)。当前没有轨道空间索引，不能把“有包围盒剔除”写成“每帧只查可见轨道”。

## 2. 当前每帧的真实时间成本

### 扫描、裁剪和生成

- HeightMapScene.build 遍历 R 条输入轨道，路线半宽计算遍历色带；即使轨道最终在屏外，部分宽度统计也已经执行。因此有 O(R + A) 成本。
- 包围盒命中的轨道在底衬/路线绘制中分别检查自己的全部线段，两次是常数倍，所以是 O(P)，不是只花 O(J)。一条很长、包围盒覆盖视口的折线可能大部分线段仍在屏外。
- 每条裁剪成功线段按 `h_i = max(1, min(256, ceil(abs(ΔY_i)/0.5)))` 分片。代码先按原线段算 h_i 再遍历所有片，因此 H = Σh_i ≤256J；很小的可见区间也可能先检查最多 256 个片。
- 每个实际非空片段生成一次灰色底衬、每条共线线路一份基础色带，以及实际命中的白块。因此 `Q_s = Σ实际可见片段(1 + K_i) + B`，这里假设轨道和路线层都开启；只开轨道时每片一份。
- 所有 C 节输入车厢做合法性、包围盒和 LOD 检查，成本 O(C)。只有通过的精细车厢进入分片。单车 `h_c = max(1, min(256, ceil(abs(frontY-backY)/0.5)))`，产生 `2h_c + 2` 个四边形，最多 514 个；平车为 4 个，低缩放列车标记为 1 个。

综合几何构建为 **O(R + A + P + H + C + Q)**。H 有固定上限因子，但实际性能分析不能把 256 当成“没有代价”。高铁白块先裁剪再枚举，不按整条屏外轨道长度产生全部白块；其成本已经计入 B/Q。坡道还会把同一个长白块切成多片。

### 排序、提交和 hover

现有代码对整个 quads 列表按 height、detail 比较排序，最坏 O(Q log Q)。输入已有序时可能更快，不能依赖所有网络/车辆状态都保持有序。

每个四边形向顶点缓冲写 4 顶点，CPU 提交 O(Q)。hover 逆序扫描 quads、每个常数时间做四边形包含判断，最坏 O(Q)，没有命中时通常会扫描到底。高度排序后的顺序用于遮挡和拾取，避免隐藏车辆仍被选中；这一要求不需要 O(C×R)。

因此当前每帧 CPU 总量可写为：

**T = O(R + A + P + H + C + Q log(Q+1))**。

在输入已按视口过滤、色带/分片生成工作按输出计的简化模型中，常写成 **O(S + C + Q log Q)**；这里 S 必须含候选线段等扫描工作，不能把扫描全网的 R/A/P 直接忽略。

GPU 还需要 O(F) 量级的片元处理；Q 相同但轨道更粗、重叠层数更多、分辨率更高，耗时也可能更高。被高架遮住的低处车厢在当前 CPU 流水线仍会生成和提交，并不因为看不到就自动零成本。

## 3. 陡坡与共线怎样放大 Q

忽略白块，K 条共线线路的单段为 `(1+K)h` 个静态四边形。分片未到上限前，数量与高度跨度/0.5 近似线性，且与色带数量相乘。

| 输入单位 | 高差 | 分片数 | 输出四边形 |
| --- | ---: | ---: | ---: |
| 1 段轨道、4 条普通共线线路 | 0 | 1 | 5 |
| 同一段 | 1.6 格 | 4 | 20 |
| 1 节车厢 | 0 | 1 | 4 |
| 同一车厢 | 4 格 | 8 | 18 |

增加平行路线既可能增加 K，也可能是另一条独立物理轨道增加线段数，二者要分别统计。当前密集共线仅限制显示总宽，超过四条线路仍会生成各条色带；低缩放关闭白块只减 B，不会自动消除 K 条基础色带。

已有 TrackSampler 每条 rail 最多 256 采样点，但这是采样上限，不是整张地图 256 个图元；后续每段仍可能细分，所以不能据此得出全网几何有很小的常数上限。

### 生产几何的数量实验

新增 `tools/HeightComplexityProbe.java`，直接调用当前 HeightMapScene。合成 100 条轨道、每条 100 段，共 10000 段，4 条普通共线线路、500 节全部可见车厢。三个场景均无白块；起伏线段用于隔离分片数量，不代表真实网络的坡度分布。

| 场景 | 轨道 Q_s | 车厢 Q_d | 合计 Q |
| --- | ---: | ---: | ---: |
| 全平 | 50000 | 2000 | **52000** |
| 每段轨道高差 1.6，车厢平 | 200000 | 2000 | **202000** |
| 每段轨道高差 1.6，车厢高差 4 | 200000 | 9000 | **209000** |

这是实际几何输出数量，不是帧率、GPU 或分配耗时基准。Q 从 52000 增至 209000 约 4.02 倍；用 Q log2 Q 估算排序工作规模约 4.53 倍，不可把这个比值当成真实排序耗时倍数。

复现（用已构建的 main classes；类源码变更后应先编译主工程）：

```powershell
New-Item -ItemType Directory -Force build/height-complexity
javac -cp build/classes/java/main -d build/height-complexity tools/HeightComplexityProbe.java
java -cp 'build/classes/java/main;build/height-complexity' HeightComplexityProbe
```

## 4. 空间复杂度与分配率

已缓存 MapTrack 的采样、距离和法线随全网采样点数线性增长。每帧新建 quads、MapVertex、ArrayList 和排序临时引用，**新增工作空间 O(Q)**，未保存所有车辆/轨道的相交关系，所以不是 O(C×R) 存储。

典型轨道 Quad 有独立的 4 个 MapVertex。仅作 HotSpot 常见布局估算，假设压缩引用、8 字节对齐：MapVertex 约 40B，Quad 约 56B，列表引用约 4B，总约 **220B/四边形**，未包含容器余量、排序临时引用及其他对象；车厢部分共享角点，实际值会有差别。没有用 JOL/JFR 测量，本数值不能当成 JVM 保证。

- Q=52000：按这个模型约 11.4MB 新场景对象。
- Q=209000：约 46.0MB。
- 如果每帧都重建且 60FPS，模型对应约 0.69GB/s、2.76GB/s 的场景分配周转。它们不是“堆必须这么大”，也不是 GC 实测，而是重复 new 的压力示意。

此外当前 contains 创建四点数组，渲染器用 List.of 包装每个 quad 顶点，宽度/裁剪有辅助对象；JIT 可能消去其中部分临时分配，不能把源码中的每个 new 都当成实测堆分配。MapVertex/Quad 已进入持久于本帧的列表，尤其静态轨道重复生成更值得优先消除。

顶点缓冲也是 O(Q) 字节，实际大小由 VertexFormat 和后端决定，不能和 Java 堆场景占用混为一谈。排序的临时引用 O(Q)，加上上一帧等待 GC 的对象，瞬时堆峰值不只一个 scene。

## 5. “0.5 格分片”不是精确遮挡保证

增加分片降低长坡段用平均高度排序的误差，但没有改变算法性质：每片仍只有一个 sortHeight。交叠范围内谁高谁低发生变化时，一个先后顺序不能同时表达整个区域。

对高度沿长度线性变化、横向无侧倾、未触发 256 上限的普通片段，0.5 格高度跨度意味着中点排序值与片内高度差最多约 0.25 格。比较两个这样的片段时，间距小于约 0.5 格的局部顺序就可能有歧义。这仅是该限定模型的误差说明，不是当前全部图元的误差上界。

车厢横向 roll、端帽单独的排序键、较陡且触及分片上限的段、几何采样误差均不满足上述简单条件。继续把阈值改小会增加 Q；不能靠无限细分获得通用正确性，也不能把整个车厢平均 Y 改成整列平均 Y。

当前测试证明选定的上跨/下穿/坡道案例，不证明任意相交曲面的逐像素可见性。需要逐像素按已给定三角面真实高度决定可见性时，应评估深度测试；它依然只对输入几何负责，不会自动补出地形或完整车厢屋顶模型。

## 6. 三条优化路线的复杂度

| 路线 | 每帧主要 CPU | 额外空间 | 特点 |
| --- | --- | --- | --- |
| 当前细分画家 | O(R+A+P+H+C+Q log Q) | O(Q) 新工作集 | 简单、无独立深度目标，但近似且静态工作重复 |
| 缓存静态片段＋索引＋合并 | 查询 + O(Q_d log Q_d) + O(Q_s+Q_d) | 静态缓存/索引 O(S_cache)，动态 O(Q_d) | 静态只在失效时生成/排序；仍保留画家算法的精度边界 |
| 缓存静态 mesh＋独立深度通道 | 查询 + 动态生成 + 提交，无统一 Q log Q | 几何缓存 + O(P_x) 深度/颜色目标 | 可按输入三角面局部高度测试，成本移向 GPU 片元/显存及集成 |

### 先做缓存与索引

静态高度片段及顺序在地图数据/样式/有关缩放参数变化时构建一次。动态四边形独立排序，与缓存静态序列线性合并即可保持同一 painter 顺序，**不能把静态一次全画完再把车厢全画上面**，否则低处列车会浮到高架上。

CPU 合并本身仍要 O(Q_s+Q_d)，它消除的是每帧静态分配和对静态数据重新比较排序，不是让静态渲染完全免费。静态构建/缓存失效还会有 O(S_cache log S_cache) 一类冷启动成本，需要分批和测量。

空间索引按轨道段/片段包围盒建，不能只索引整条巨大的铁路；典型 R-tree 查询可按“约 log S + 返回候选数”估算，但大量包围盒重叠时最坏仍可退化到 O(S)。同样为 hover 建索引，鼠标下查 k 个候选再做高度/包含判断；期望代价降低，极端多层堆叠时 k 本身仍大。

像素线宽、白块 LOD 与缩放相关，裁剪也与视口相关：缓存键/失效策略必须包含这些因素，或缓存未裁剪片段再做轻量查询。不能声称移动/缩放时所有静态几何永远不变。高铁纹理按可见分块惰性生成，避免为一条极长屏外轨道预先生成全部白块。

### 更严格遮挡：独立深度通道

把地图 X/Z 映射到屏幕 X/Y，将真实世界 Y 映射到独立、受控的深度范围，让高处的片元覆盖低处。OpenGL 的深度比较与深度写入是分开的状态，必须两者配置正确并拥有相应深度缓冲，不能只调用 enableDepthTest 就认为生效。依据 [Khronos glDepthFunc](https://github.com/KhronosGroup/OpenGL-Refpages/blob/main/gl4/glDepthFunc.xml) 和 [glDepthMask](https://github.com/KhronosGroup/OpenGL-Refpages/blob/main/gl4/glDepthMask.xml)。

现有两个渲染器把 GUI Z 固定为 0，高度只用于 CPU 排序；改用深度不是一个配置开关。建议在专用 overlay render target 中完成颜色/深度，再合成回地图，避免污染宿主地图/tooltip 的 GUI 深度。共面底衬、线路白块、描边和车厢优先级要显式处理；透明色带不能因写入错误深度造成假遮挡。目前灰色底衬和车厢外层不透明，可作为明确的遮挡面。

这个方案不再需要**仅为了高度排序**而按 0.5 格纵向细分，曲线几何/法线/纹理所需的细分仍保留。CPU 比较排序可以去掉，GPU 一帧工作模型约 **O(Q + F + P_x)**：顶点、片元以及清除/合成。它不是“GPU O(1)”；若大量四边形覆盖同一大屏区域，F 最坏可达 O(Q×P_x)，早期深度拒绝的收益取决于顺序/材质/硬件。

假设 RGBA8 颜色＋每像素 4B 深度且无 MSAA：1920×1080 的目标合计约 **15.8MiB**，3840×2160 约 **63.3MiB**，不含宿主缓冲、顶点缓存、双缓冲及可选 ID 缓冲。这里是实际渲染目标像素分辨率，不是 GUI 逻辑尺寸。MSAA 会增加存储与处理，必须单独算。

hover 仍需与可见性一致：可以对鼠标下候选三角面插值局部 Y 并比较，或另做对象 ID pass。不能改了 GPU 画面却继续按旧平均高度拾取。每帧同步读取 GPU 结果也可能带来等待，具体方案需要原型测量。

## 7. 不建议的做法与最终顺序

- 每节车厢扫描所有轨道做相交/高低判断：朴素 O(C×S)，大量无关比较；当前算法并没有这么做。
- 为“严格排序”枚举所有静态片段相交并持续切割：最坏投影交叉数本身可达平方级，容易产生巨大预处理/输出，不宜作为常规逐帧流程。
- 仅按整数 Y 分桶声称线性且精确：同桶内高度仍不同，会损失小高差遮挡；若桶内继续比较，则仍有局部排序成本。
- 只缓存一张没有高度信息的静态背景：车厢无法和高架交换遮挡关系。
- 地图隐藏仍更新场景、全网所有车厢逐帧求解：把通信 LOD 与渲染可见性分离后，应只给可见车厢求精细姿态。

建议顺序是：**统计每帧 R/P/Q_s/Q_d/B 与分配 → 静态缓存、复用顶点/数组 → 段级空间索引与 hover 索引 → 评估深度渲染原型**。若已明确要求比片段画家更严格的局部遮挡，深度原型可与缓存设计一起做，避免把缓存烘焙成无法再按高度遮挡的格式。

服务器不应为每个玩家计算地图下穿可见性；同步真实 XYZ/路径/姿态即可，遮挡在客户端视口完成。已有 XYZ 数据下，下穿不会额外要求每帧网络往返。网络采集成本、静态 Y 的存储与传输、客户端遮挡开销分别报告。

本轮实际执行：数量 probe 编译/运行通过，结果与上表一致；未做帧耗时、JFR、GPU 或专用深度通道实测。版本与运行代码不变。
