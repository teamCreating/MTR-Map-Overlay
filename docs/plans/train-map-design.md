# 列车车厢、运行线路与到站预测设计

日期：2026-10-19 20:50（Asia/Taipei）。操作者：Codex。

状态：设计方案，未实现。基线：main `522d3c1`，MC 1.21.1，MTR 4.1.0-beta.2，NeoForge/Fabric；静态地图同步为 v6。本次不修改功能源码、版本号或发布产物。

## 1. 目标与关键决策

放大地图时显示每节车厢的真实位置与朝向；悬停任意车厢获得整列车的当前线路、运行目的地、下一停靠站、沿实际路径的剩余距离及预计到达时间。站点界面显示按站台、线路和方向区分的后续班次。车辆和站点使用同一个预测来源。

核心决策：

1. 运行车辆、运行班次、路线、车型是不同对象，必须分别编号。
2. 车厢沿 Core 的有序实际行驶路径定位；目前的二维地图线和去重 trackIds 不能直接承担此职责。
3. 服务端采集权威状态，客户端只做显示插值，不在 mod 中再实现一套行车、制动或信号模拟。
4. ETA 复用 Core 预测，明确区分实时预测、时刻表、无数据和过期。关联不唯一时不显示该列车 ETA。
5. 动态列车流独立于静态 v6 快照；地图不打开时停止订阅，无订阅者时停止导出。
6. 首个实现先验证单列车准确性，再优化全网规模。不能把当前“车辆小圆点预计工作量小”的旧任务描述当作完整车厢/ETA的工作量判断。

| 线路信息 | 当前/前一/后一线路、站台、站点及目的地可读 | 正式定义当前服务段的状态机，不能机械地把所有 `next*` 当“下一次停靠” |

### 现有地图模型不能直接复用的部分

- `MapRoute.trackIds` 经 distinct 去重，不保留轨道的重复经过、完整顺序和沿轨方向。
- `MapTrack` 只存 X/Z；其累计距离是投影折线长度，不是 Core 路径里程。坡道会造成里程误差。
- `TrackPatternLayout` 的方向、相位只用于静态线路纹理；在道岔重新起链，不能当列车运行方向或导航路径。
- `MapLandmark` 的平台 ID 目前是带前缀的展示字符串。ETA 查询应保留规范化数值 platformId，避免用展示文本或站名反查。
- 当前客户端回退用整条车辆路径给“当前线路”染色，不能据此认定未来所有路段都属于同一服务线路。

## 3. 身份模型与服务段

| 对象 | 建议身份 | 生命周期 |
| --- | --- | --- |
| 列车实体 | serverSessionEpoch + dimension + vehicleId | 实体创建到移除；同一实体可服务多条线路 |
| 运行班次 | sidingId + departureIndex + departureTime/offset + Trip 身份 | 班次发车至结束，循环时区分运行实例 |
| 停靠事件 | 班次身份 + tripStopIndex + 圈次/出现序号 | 同一站台重复经过仍是不同事件 |
| 路径定义 | pathKey + revision | 行车路径或其里程、停靠序列变化时失效 |
| 编组定义 | consistKey + revision | 车厢数量、车型、尺寸、转向架或车钩间距变化时失效 |
| 车厢 | 列车身份 + 稳定车厢索引 | 折返不重排逻辑身份，运动前端可以变成末节 |

不得用颜色、线路名称、车型 ID 或 OBA 展示 vehicleId 代替列车实体 ID；`departureIndex` 也不保证跨 Siding、跨循环实例唯一。

运行状态至少包含：RUNNING、DWELLING、RETURNING、MANUAL、OUT_OF_SERVICE、UNKNOWN。只有 Core 明确提供依据时才进一步显示“等信号”，不能仅凭速度为零推断。服务信息提供当前线路、目的地、下一停靠事件，并允许无有效服务信息。

Core this/next 字段必须用行进中、进站、开门、离站、折返、贯通换线的实际样例核验。不要只按速度切换字段，也不要在全网路线表里选一条同色线路凑信息。

## 4. 车厢位置与绘制

### 4.1 两种位置方案

| 方案 | 优点 | 成本及边界 | 定位 |
| --- | --- | --- | --- |
| 服务端逐车厢姿态快照 | 容易对照 Core；不依赖客户端重建全部细节 | CPU、对象分配和带宽随车厢数增长；XYZ直线插值会切弯 | 小范围准确性原型、特殊车辆回退 |
| 路径/编组定义 + 列车进度流 | 运行包接近按列车计费；同路径复用；沿轨插值 | 必须正确还原里程、方向、车钩、转向架、路径修订 | 正式方案首选，但以姿态对照验收为前提 |

先用第一种验证字段和交互，再用同一场景验证第二种。若某类编组无法通过姿态精度测试，可对选中/可见列车回退姿态快照，不能用错误的贴轨位置强行上线。

### 4.2 路径定义

车辆路径是有序段列表；每一段包含 railId、轨道方向、Core 累计起止里程、停靠 occurrence，并引用共享的轨道几何。即使同一 railId 出现多次也不得去重。

几何点需保留 Core 原生轨道参数与 XYZ 对应关系。优先用 Core 几何函数或带误差控制的采样；不能把现有 X/Z 折线长度直接当 Core 里程。按里程定位段后再求位置，保留跨轨道边界所需的历史段和编组后部路径。

循环、里程回绕、折返、人工倒车、路径重生成和传送均为明确的不连续事件：更新 run/path generation 并重置插值，不允许跨旧/新定义之间插值。

### 4.3 车厢姿态

- 使用 Core 编组数据还原每节前后转向架及车体前后悬，不能简单把车头倒退 N×车长。
- 车体是刚性矩形，沿前后转向架确定位置/朝向；不是把整个车体画成沿弯道弯曲的线。
- 单转向架车辆用局部轨道切线补齐方向；长车、非对称车体、混编、车钩间距和折返均有专门测试。
- 稳定车厢索引与运动方向分开；车头箭头标实际前进端。
- 服务端状态/定义不可变，客户端仅插值，不调用 Core 完整 simulate，也不篡改 live VehicleExtension 的 railProgress。

### 4.4 地图表现

- 大比例尺：逐车厢绘制矩形，适当车间隙，所属线路颜色＋深色/浅色对比边框；悬停任意节显示整列车信息，可附“第 3/8 节”。
- 中比例尺：简化编组轮廓或短条；小比例尺：一个带方向的列车标记。阈值根据车厢实际投影尺寸及迟滞切换，避免缩放闪烁。
- 车厢位置落在真实物理轨道中心，不为了对齐彩虹色带把列车横移到假位置。悬停时高亮其所属线路色带。
- 多列车屏幕重叠时允许选择候选列表；保留 Y、轨道 ID，区分上下层线路。不能仅用 X/Z 最近点判断换轨或层级。
- 轨道、路线、列车、地标、选中轮廓/提示按明确层级绘制；车厢可见性和站点标志的优先级一起验收。
- Xaero 与 JourneyMap 共用 MapTrain/车厢纯几何、命中检测和 tooltip 数据，两端仅负责投影、批绘制和 UI 接入。
- 命中检测只覆盖可见车厢，先空间索引/包围盒，再做旋转矩形检测；停留约 150ms 后请求详细 ETA，点击可固定面板，避免鼠标扫过触发大量查询。

建议悬停信息：

```text
东铁线 · 往罗湖
SP1900 · 8 节编组（当前第 3 节）
下一站：大学 · 2 号站台
沿轨距离：约 1.2 km
预计到达：约 1 分 40 秒（Core 实时预测）
状态：运行中
```

名称、站名与数字来自数据；例子只定义格式。目的地可以是自定义显示文本或环线说明，不能总称“终点站”。

## 5. 动态订阅与时钟

### 通道与缓存

保留静态 v6，增加独立、有版本的动态能力协商与 payload。对端无动态能力时，静态地图照常工作；无服务端组件时，使用 MTR 附近车辆并标记“附近数据”，不能假称全网。

拟分为 Subscribe/Unsubscribe、Definitions、TrainFrame、ArrivalDetails 四类。订阅以正在查看的维度为主，附视口/缩放/选中列车。用短租约定期续租，关闭地图、切服、切维度、断线或客户端异常不续租时清理。服务端限制订阅范围和请求频率。

一次每维度采集供所有订阅者复用，再过滤可见范围、选中列车及缓存区；不为每个玩家重复遍历 Core，也不在每个请求里重建路径或静态快照。

Definitions 保存可复用路径、编组和服务文本；TrainFrame 保存轻量 upsert/delete、定义引用、时间和状态。普通服务信息改变时更新元数据，不必重发几何。

每帧包含 sessionEpoch、dimension、subscriptionGeneration、sequence、Core sampleTime；状态引用 path/consist revision。未知定义等待补发而不是按旧定义绘制。关键帧/完整集合修复漏删与缓存不一致，明确区分视口移出和实体销毁。

### 插值与新鲜度

初始位置更新取 2Hz，选中列车/近景可升至 5Hz；均为待测默认值。客户端保留约一个采样间隔的缓冲并沿路径插值，接受一定显示延迟来减少抖动。先保证正确，不默认增加无界外推。

流中断约 3 秒标记过期、约 10 秒隐藏（选中面板可保留“失去更新”）。这些是初始产品参数，后续按延迟测试调整。在流正常时，通过完整集合/明确删除维护静止列车的存在，不能因为“没有运动增量”就淘汰站内列车。

ETA 时间基于 Core sampleTime 与预测时间戳计算，再锚定客户端单调时钟；估计服务器偏移/RTT并检查时间跳变。不能盲减客户端系统时间，也不能把 Minecraft 日夜游戏时间当预测时间轴。

## 6. ETA：来源、身份与边界

### 6.1 直接复用 Core 预测

到站时间与发车时间分别保存；保留 deviation 和 realtime。不要把已经包含 deviation 的 arrival 再加一次偏差。Core 的预测基于其模拟/时刻机制，不保证能预知后续所有信号拥堵或人工操作。

仅有时刻表时显示“计划到达”；等信号/人工驾驶或预测失效时保留不确定性，必要时显示“暂无可靠预测”。过期、取消、已停靠、终到应有独立状态。数据失效后不继续倒数成负值，也不把站内停车显示成无限到站时间。

### 6.2 最重要的接口验证关卡

`ArrivalResponse` 对实际车辆的关联上下文不够完整。相同 routeId/platformId/departureIndex 可能来自不同 Siding、班次循环或同一站台的重复停靠。

首选方案是在 Core 预测生产边界取得一次结构化记录：

```text
actualVehicleId? + sidingId + departureIndex + departureOffset
+ trip identity + tripStopIndex/visitOccurrence
+ platformId + routeId + arrival + departure + deviation + realtime
```

当前内部回调已有大部分字段，但方法和嵌套回调类型不是公开 API。P0 必须验证能否以稳定的访问拓宽/命名方法桥接保留它们；不能认为加一个普通 @Invoker 就必然可用，也不能把注入编译器生成的 lambda 当长期接口。

若访问桥接不可维护，考虑最小公开 Core 导出接口（不改变预测算法），再评估是否需要单独发布兼容 Core。不能未经验证承诺完全零 Core 改动。

保守回退可以在 Siding 上下文中调用公开 getArrivals，再按班次、路线、站台和时间窗口唯一匹配。计数截断、循环或停靠出现序号导致歧义时，只显示站台预测，不给具体列车硬贴 ETA。没有 actualVehicleId 的计划班次也不能画成“正在运行的列车”。

### 6.3 距离与目标停站

距离来自下一次有效客运停靠目标的 Core 路径里程，减去同一里程域内的车辆参考进度。必须使用对应方向、圈次和 occurrence；折返的运动前端和停车基准要与 Core 一致。

不能直接使用 getStoppingPoint：该值也用于临时/信号停车。不能用最近车站、路线最后一个站、两点直线距离，或“距离÷当前速度”替代行车预测。

到站/离站状态切换由停靠事件驱动。默认展示到下一客运站的距离；等待进站时继续指向该站，站内开门显示“已到站”，发车后切到下一停靠。回库/无服务明确显示，不伪造客运下一站。

### 6.4 站点与列车面板共享结果

选择站点后，先展开真实 platformId，再按站台＋routeId＋方向/目的地展示未来 3–5 班。不同站台或目的地即使同色也不合并。去重键保留班次和停靠 occurrence。

选中列车初始只取下一停靠及随后最多 2 个停靠的详情；站点面板约 1Hz 更新，同一查询共享缓存。普通悬停即时显示本地位置/线路，详细预测异步补齐。

注意：公开 getArrivals 的内部实现会遍历时间窗口并排序，再截取 count。不能把 count=1 当作 O(1)，也不能为 N 列车每秒查询所有站。若必须用此接口，按所需 Siding/站台批处理、去重和限频，单独测量开销。

## 7. 性能设计与预算

以下是设计预算，不是实测成绩。

- 服务端共享采集约按 Siding 数＋车辆数增长；轻量进度读取避免逐车厢姿态分配。
- 客户端姿态计算约按可见车厢数增长，路径段用二分或游标；不对全网车辆逐帧做完整 Core 物理模拟。
- 路径定义按 revision 建立/共享，不能在高频循环中计算完整路径哈希或序列化整个 VehicleExtraData。
- 可见车厢在合适 LOD 下一批绘制；悬停只检测可见对象，文本仅为选中/悬停对象构建。
- 模拟线程只复制一致状态，编码、压缩、分块和网络发送移出；任务合并、有界排队，忙时丢弃旧快照而非积压。
- 隐藏地图不订阅、无人订阅不采集；全网小比例尺使用粗略标记，近景精细路径/编组按需补齐。

若轻量动态记录控制在每列 80–128 字节，1000 列车、2Hz、单客户端有效载荷约 160–256KB/s；10 个客户端全量订阅约 1.6–2.56MB/s。定义、ETA、包头另计，压缩收益未计。进度方案降低随车厢数增长的流量，但仍随订阅者数量增长，必须做范围过滤。

先固定测试主机和场景，再把初始验收预算设为：1000 列车、2Hz 下模拟线程采集 P95 不高于约 2ms/次；60FPS 下 1000 节可见车厢的增量渲染预算约 1.5ms/帧。定义传输/路径建立和 ETA 查询单独计时，不能藏在平均值里。预算不通过时优先降低订阅范围、更新频率、LOD和分配量，不能宣称测试未做就“开销可忽略”。

基准矩阵：100/1000/5000 列车；1/8/16 节编组；1/10/30 个订阅者；1/多维度；直线/曲线/坡道/共线/折返；低/高网络延迟。记录 P50/P95/P99、GC分配、发包字节、模拟积压、客户端帧时间、可见对象数及 ETA 刷新耗时。

## 8. 分阶段实施与验收门
